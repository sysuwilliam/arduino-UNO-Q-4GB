+# TEB Local Planner 接入与调参方案
+
+## 目标
+
+将当前 `Nav2 + DWB` 的局部规划方案切换为 `Nav2 + TEB`，并建立一套可重复的仿真调参与真机验证流程。
+
+当前仓库中与 Nav2 相关的主配置位于：
+
+- `venom_bringup/config/scout_mini/nav2_params.yaml`
+- `venom_bringup/config/sentry/nav2_params.yaml`
+
+仓库中还保留了一份旧的 TEB 配置样例：
+
+- `venom_bringup/config/nav2_params_scoutmini.yaml`
+
+## 接入方案
+
+### 1. 依赖准备
+
+需要先确认运行环境中存在可被 `pluginlib` 加载的 TEB 插件实现。如果环境中没有 `teb_local_planner::TebLocalPlannerROS`，`controller_server` 启动时会直接报错。
+
+实施前应确认：
+
+- TEB 插件已经安装或已经作为工作区源码引入
+- 插件导出信息完整，能被 `pluginlib` 发现
+- 与当前 ROS 2 / Nav2 版本兼容
+
+### 2. Nav2 配置切换
+
+在 `controller_server` 下，将：
+
+```yaml
+controller_plugins: ["FollowPath"]
+
+FollowPath:
+  plugin: "dwb_core::DWBLocalPlanner"
+```
+
+替换为：
+
+```yaml
+controller_plugins: ["FollowPath"]
+
+FollowPath:
+  plugin: "teb_local_planner::TebLocalPlannerROS"
+```
+
+建议先只改一个平台，例如先改 `scout_mini`，确认稳定后再迁移到 `sentry`。
+
+### 3. 参数迁移策略
+
+不要直接保留 DWB 的评分参数。下面这些参数是 DWB 专属，应当删除或停用：
+
+- `vx_samples`
+- `vy_samples`
+- `vtheta_samples`
+- `critics`
+- `PathAlign.scale`
+- `GoalAlign.scale`
+- `PathDist.scale`
+- `GoalDist.scale`
+- `RotateToGoal.scale`
+
+保留的通常是与控制器无关或弱相关的通用项：
+
+- `controller_frequency`
+- `min_x_velocity_threshold`
+- `min_y_velocity_threshold`
+- `min_theta_velocity_threshold`
+- `progress_checker`
+- `goal_checker`
+
+然后补齐 TEB 参数。
+
+## 关键参数
+
+TEB 的关键参数建议按下面几组来调。
+
+### 1. 时域与轨迹离散
+
+- `teb_autosize`
+- `dt_ref`
+- `dt_hysteresis`
+- `max_samples`
+- `global_plan_prune_distance`
+- `max_global_plan_lookahead_dist`
+
+作用：
+
+- 控制轨迹时间分辨率和优化规模
+- 影响轨迹平滑性、响应速度和计算负载
+
+建议：
+
+- 先用中等 `dt_ref`，避免离散过细导致计算压力过大
+- 先限制 `max_global_plan_lookahead_dist`，避免局部规划器一次吞入过长路径
+
+### 2. 机器人运动学与动力学
+
+- `max_vel_x`
+- `max_vel_x_backwards`
+- `max_vel_y`
+- `max_vel_theta`
+- `acc_lim_x`
+- `acc_lim_theta`
+- `min_turning_radius`
+- `wheelbase`
+- `cmd_angle_instead_rotvel`
+
+作用：
+
+- 约束 TEB 输出是否符合底盘真实能力
+- 决定转弯半径、倒车能力和姿态变化速度
+
+建议：
+
+- 差速底盘通常设 `max_vel_y: 0.0`
+- 差速底盘通常从 `min_turning_radius: 0.0` 开始
+- 真机前不要把最大速度和最大角速度一次设到极限
+
+### 3. 目标容差与终点行为
+
+- `xy_goal_tolerance`
+- `yaw_goal_tolerance`
+- `free_goal_vel`
+
+作用：
+
+- 决定接近终点时是否容易抖动、绕圈或反复修正
+
+建议：
+
+- 初期将 `xy_goal_tolerance` 和 `yaw_goal_tolerance` 设得略宽
+- 先消除终点抖动，再逐步收紧容差
+
+### 4. 全局路径跟随行为
+
+- `global_plan_overwrite_orientation`
+- `allow_init_with_backwards_motion`
+- `global_plan_viapoint_sep`
+- `exact_arc_length`
+- `feasibility_check_no_poses`
+
+作用：
+
+- 决定 TEB 如何理解全局路径方向、是否允许倒车、是否更积极地贴合路径
+
+建议：
+
+- 如果机器人不希望倒车，先保持 `allow_init_with_backwards_motion: False`
+- 如果轨迹偏离全局路径明显，再考虑 `viapoint` 相关约束
+
+### 5. 机器人外形与碰撞模型
+
+- `footprint_model`
+- `min_obstacle_dist`
+- `inflation_dist`
+
+作用：
+
+- 决定局部规划绕障的保守程度
+- 直接影响贴边、卡角、擦碰风险
+
+建议：
+
+- `footprint_model` 必须与真实底盘外形一致
+- 先从略保守的障碍距离开始，稳定后再压榨通过性
+
+### 6. 优化权重
+
+常见项包括：
+
+- `weight_max_vel_x`
+- `weight_max_vel_theta`
+- `weight_acc_lim_x`
+- `weight_acc_lim_theta`
+- `weight_kinematics_nh`
+- `weight_kinematics_forward_drive`
+- `weight_optimaltime`
+- `weight_obstacle`
+
+作用：
+
+- 决定轨迹是更激进、更平滑，还是更守障碍边界
+
+建议：
+
+- 初始阶段少量改权重，优先先把运动学和障碍距离调准
+- 如果已经频繁碰障，再加大 `weight_obstacle`
+- 如果原地抖动或过于保守，再检查 `weight_optimaltime` 与容差参数
+
+## 推荐调参顺序
+
+建议按下面顺序推进，避免同时动太多变量。
+
+1. 跑通插件加载
+2. 确认底盘速度、加速度和 footprint 合理
+3. 确认能稳定跟踪直线路径
+4. 确认 90 度转弯不过冲、不原地抖动
+5. 确认窄通道绕障行为
+6. 最后再调优化权重和终点容差
+
+## 仿真调试流程
+
+仿真环境优先使用 `simulation/venom_nav_simulation`。
+
+### 1. Gazebo 中重点观察
+
+在 Gazebo 中重点看：
+
+- 机器人是否出现明显急停急转
+- 转弯时是否切角过大
+- 窄通道中是否左右来回摆动
+- 避障时是否出现死锁或原地振荡
+- 倒车策略是否符合预期
+
+建议的测试场景：
+
+- 长直走廊
+- 90 度拐角
+- S 弯
+- 窄门通过
+- 障碍物贴边绕行
+
+### 2. RViz 中重点观察
+
+在 RViz 中建议同时显示：
+
+- Global Path
+- Local Path / Trajectory
+- Local Costmap
+- Global Costmap
+- RobotModel
+- TF
+- LaserScan 或 PointCloud
+- Footprint
+
+要重点判断：
+
+- 局部轨迹是否始终贴近全局路径
+- 轨迹是否反复左右切换
+- 轨迹终点是否落在合理前视距离内
+- 局部 costmap 中的障碍是否与传感器数据对齐
+
+### 3. 仿真调参节奏
+
+建议使用固定流程：
+
+1. 只改一组参数
+2. 记录改动前后的现象
+3. 每次只验证 1 到 2 个典型场景
+4. 参数稳定后再切到更复杂场景
+
+推荐先调：
+
+- `max_vel_x`
+- `max_vel_theta`
+- `acc_lim_x`
+- `acc_lim_theta`
+- `xy_goal_tolerance`
+- `yaw_goal_tolerance`
+- `min_obstacle_dist`
+- `dt_ref`
+
+## 真机调试流程
+
+真机调试必须比仿真保守。
+
+### 1. 真机前置检查
+
+- `base_link`、`odom`、`map` 坐标链稳定
+- 里程计方向正确
+- 激光或点云障碍与实际位置一致
+- `footprint_model` 与真实外形一致
+- 最大速度与加速度不超过底盘可控范围
+
+### 2. 真机调试顺序
+
+1. 空旷区域低速直行
+2. 低速转弯
+3. 小角度避障
+4. 终点停车稳定性
+5. 窄通道通过
+6. 高频连续目标切换
+
+### 3. 真机常见问题与优先检查项
+
+如果出现轨迹振荡，先查：
+
+- `acc_lim_x`
+- `acc_lim_theta`
+- `xy_goal_tolerance`
+- `yaw_goal_tolerance`
+- `min_obstacle_dist`
+- 定位噪声和 TF 抖动
+
+如果出现贴障过近，先查：
+
+- `footprint_model`
+- `min_obstacle_dist`
+- `inflation_dist`
+- costmap 分辨率和障碍层配置
+
+如果出现转不过弯，先查：
+
+- `max_vel_theta`
+- `acc_lim_theta`
+- `min_turning_radius`
+- `wheelbase`
+
+## Gazebo、RViz、dynamic configure 的使用方式
+
+### 1. Gazebo
+
+Gazebo 的作用是快速暴露运动学和碰撞模型问题。
+
+建议：
+
+- 使用固定地图反复回放同一路线
+- 每次只调整一类参数
+- 对比相同起终点下的轨迹变化和耗时变化
+
+### 2. RViz
+
+RViz 的作用是看清“为什么错”，而不是只看“是否撞了”。
+
+重点观察：
+
+- 全局路径和局部轨迹的偏差
+- footprint 与障碍边界的关系
+- 目标点附近的姿态调整过程
+- costmap 是否过度膨胀或漏障
+
+### 3. dynamic configure
+
+需要区分 ROS 1 和 ROS 2。
+
+- 如果使用的是 ROS 1 风格的 `teb_local_planner`，常见做法是配合 `rqt_reconfigure` 做在线调参
+- 如果使用的是 ROS 2 / Nav2 方案，通常不再依赖传统 `dynamic_reconfigure`
+
+对当前仓库这类 ROS 2 场景，建议这样做：
+
+- 首选 YAML 参数文件管理
+- 小步修改后重启 `controller_server` 或整套 Nav2
+- 配合 RViz 与日志做回归对比
+
+如果所用 TEB 插件版本支持 ROS 2 参数热更新，再补充在线改参流程；否则不要把调参流程建立在 `dynamic_reconfigure` 之上。
+
+## 建议的落地步骤
+
+1. 先在 `scout_mini` 上建立一份独立 TEB 参数文件
+2. 保留 DWB 原文件，避免一次性覆盖
+3. 在仿真中完成基础运动学、障碍距离和终点行为调参
+4. 在真机低速场景完成安全验证
+5. 稳定后再迁移到 `sentry`
+
+## 建议的文件组织
+
+建议不要直接覆盖现有 DWB 文件，而是新增例如：
+
+- `venom_bringup/config/scout_mini/nav2_params_teb.yaml`
+- `venom_bringup/config/sentry/nav2_params_teb.yaml`
+
+这样可以通过 launch 参数切换 DWB / TEB，方便 A/B 测试与回退。
+
+## 成功标准
+
+完成接入后，至少应满足：

你跟我讲讲TEB的基本原理

Assistant 2026-04-27T12:28:12.753Z

TEB 的核心思路是把“局部路径规划”变成一个带时间信息的轨迹优化问题。

它不是像 DWB 那样先采样很多速度命令再打分选一个，而是直接优化一条短时域内的轨迹。TEB 里的 Timed Elastic Band 可以理解成“一串带时间间隔的轨迹点”，像一根有弹性的带子，被目标、障碍物、速度上限、加速度上限、非完整运动学约束这些因素一起拉扯，最后收敛成一条可执行轨迹。

基本组成有三部分：

  • 轨迹状态 轨迹由一串位姿点 x, y, theta 和相邻点之间的时间间隔 dt 组成，所以它优化的不只是“走哪条线”，还包括“每段多久走完”。

  • 约束与代价 TEB 会把很多要求写成优化项，比如：

  • 离障碍物保持距离
  • 不超过最大速度和最大加速度
  • 满足差速车/阿克曼车的运动学约束
  • 尽量快到目标
  • 尽量贴近全局路径

  • 尽量减少不必要倒车或大幅转向

  • 求解器优化 它把这些项组成一个稀疏优化问题，迭代求解，得到一条局部最优轨迹，然后从轨迹前段提取控制命令发给底盘。

你可以把它和 DWB 这样对比：

  • DWB
  • 采样很多速度候选
  • 向前模拟短时间运动
  • 给每条候选轨迹打分
  • 选分数最好的速度

  • 更像“离散搜索 + 打分”

  • TEB

  • 直接维护一条带时间参数的轨迹
  • 连续优化整条轨迹
  • 同时考虑路径形状和时间分配
  • 更像“约束优化”

TEB 的优势通常是：

  • 轨迹更平滑
  • 对非完整约束处理更自然
  • 对窄通道、绕障、带转弯半径约束的问题更强
  • 可以同时优化“怎么走”和“走多快”

它的代价也很明显：

  • 参数更多，更难调
  • 对机器人模型、footprint、障碍距离、定位质量更敏感
  • 如果约束冲突或参数不合适，容易抖动、绕圈、卡住

在 Nav2 场景里，你可以把 TEB 理解成： - 全局规划器负责给一条大方向路径 - TEB 负责把这条路径在局部窗口内变成一条满足底盘动力学和避障要求的可执行轨迹

为什么它比 DWB 更容易在窄通道里表现不同

Assistant 2026-04-27T12:36:07.075Z

因为 TEB 和 DWB 解决问题的方式本质不同，所以在窄通道这种“约束很紧、可行空间很小”的场景里，表现差异会被放大。

先说核心区别：

  • DWB 是“采样很多速度命令，再给每条短时轨迹打分”
  • TEB 是“直接优化一整段局部轨迹，并同时满足时间、障碍、运动学约束”

窄通道里之所以差异明显，主要有这几个原因。

  1. 窄通道本质上是“可行解很少” 在宽阔区域，很多速度命令都能走，DWB 就算采样粗一点也容易找到还不错的解。
    但在窄通道里，可执行轨迹往往只剩很小一簇，稍微偏一点就碰障。

这时： - DWB 依赖采样密度，如果采样不够细，可能根本没采到那条“刚好能过”的轨迹 - TEB 是在已有轨迹上连续优化，更容易把轨迹慢慢挤压到那条狭窄可行走廊里

  1. TEB 显式优化“整条轨迹”，不是只看瞬时速度 DWB 每个周期主要是在比较“当前发哪组速度更好”，虽然也会短时前向模拟，但本质仍偏局部决策。
    窄通道里，很多时候你需要为了后面能通过，前面先做一个不那么直观的姿态调整。

TEB 更容易做到这点，因为它优化的是一串位姿点加时间间隔： - 会提前为后续拐角留姿态 - 会在整段轨迹上平衡“贴路径”和“避障” - 更容易形成连续、平滑的穿越动作

而 DWB 容易出现： - 当前看着都不够好 - 每周期都在左右摇摆地选“局部最优” - 结果表现成走廊中来回摆动或原地犹豫

  1. TEB 对非完整运动学约束处理更直接 差速车、阿克曼车不是想往哪瞬移就往哪，它们转弯、侧向运动都有限制。
    窄通道往往正好逼着机器人在很小空间内完成姿态调整，所以运动学约束特别重要。

TEB 会把这些约束直接放进优化里： - 最大速度 - 最大加速度 - 转弯半径 - 非完整约束

所以它求出来的轨迹，通常更像“机器人真实能走出来的轨迹”。

DWB 虽然也考虑这些限制，但方式更偏“采样后淘汰”。在窄通道中，这种方式更依赖参数是否刚好合适。

  1. 障碍距离在 TEB 里是连续约束，在 DWB 里更像评分项 窄通道的关键不是“离障碍越远越好”，而是“既不能碰，又要刚好能过”。

TEB 会把障碍距离作为优化目标的一部分，让轨迹在“安全”和“可通过”之间找平衡。
这使它在理论上更擅长处理两侧都很近的情况。

DWB 常见情况是： - 障碍代价太重：不敢走，停住或抖动 - 障碍代价太轻：敢走，但贴边过近 - critic 权重稍不合适，就会在两边障碍之间反复横跳

  1. 代价是 TEB 对参数和模型更敏感 这也是“更容易表现不同”的另一面。
    TEB 在窄通道里有时明显更好，但如果：
  2. footprint 不准
  3. 障碍层不准
  4. min_obstacle_dist 太大或太小
  5. 定位抖动
  6. 运动学参数不真实

它也会比 DWB 更容易出奇怪行为，比如： - 原地抖动 - 倒车犹豫 - 轨迹反复重构 - 明明能过却判成不可行

所以更准确地说，不是“TEB 一定比 DWB 更强”，而是：

  • 在窄通道这类强约束场景中，TEB 的优化式方法更容易体现优势
  • 同时，它也更容易把模型误差和参数问题暴露出来

如果结合你这个项目里的 scout_mini，实际最该关注的就是这几项： - footprint_model - min_obstacle_dist - inflation_dist - max_vel_x - max_vel_theta - acc_lim_theta - xy_goal_tolerance - yaw_goal_tolerance
