现在缺的是 point_lio 包，不是刚才的 Livox 了。

你启动参数里写了：

lio:=pointlio

所以 launch 会去找 ROS 包 point_lio，但当前环境里没有编译/安装它。

先查源码有没有：

cd ~/venom_ws
find src -maxdepth 8 -type f -name package.xml | xargs grep -H "<name>point_lio</name>"

如果有输出，说明源码在，只是没编译。那就编译它：

cd ~/venom_ws
source /opt/ros/humble/setup.bash
source install/setup.bash

colcon build --symlink-install --packages-select point_lio \
  --cmake-args -DCMAKE_BUILD_TYPE=Release

source install/setup.bash

然后再启动仿真。

如果没有输出，说明你重装后 Point-LIO 源码没拉下来。你可以再查一下目录：

find ~/venom_ws/src -maxdepth 8 -iname "*point*lio*" -o -iname "*Point-LIO*"

另外，如果你只是想先把仿真启动起来，不一定非要用 pointlio，可以临时换掉 lio 参数，比如先不用它或用项目已有的其他选项。但你之前一直用的是：

lio:=pointlio

所以最终还是需要把 point_lio 这个包恢复并编译出来。

这个不是致命编译/启动错误，是 Point-LIO 实时处理跟不上 IMU 输入：

Point-LIO realtime warning: dropped old IMU sample(s)
imu_queue=400 max_imu_queue=400

意思是 /livox/imu 的 IMU 数据进得太快，Point-LIO 消费不过来，队列满了，就开始丢旧 IMU。常见原因：

  • Gazebo + RViz + Point-LIO + slam_toolbox 一起跑，CPU 压力太大；
  • 仿真时间步太快或传感器频率太高；
  • Point-LIO 初始化阶段还没跟上；
  • 同时开 nav_rviz:=True 会更吃资源。

你后面的这些：

rviz2 exit code -11
Cannot shutdown a ROS adapter that is not running

是你 Ctrl-C 退出后的清理问题，RViz 崩了一下，不是主要问题。

先按这个顺序处理：

  1. 先关 RViz 测一下 Point-LIO 是否稳定
ros2 launch rm_nav_bringup bringup_sim.launch.py \
  world:=RMUL \
  mode:=nav \
  lio:=pointlio \
  localization:=slam_toolbox \
  lio_rviz:=False \
  nav_rviz:=False

如果不刷屏了，说明主要是资源不够。

  1. 降低 Gazebo 压力

启动后看 CPU，如果很高，先不要开 RViz 和导航目标测试。可以用：

htop
  1. 只想调导航参数的话，可以考虑不用 Point-LIO

你现在主要是在调 TEB，不一定每次都要跑重 LIO。可以看 launch 支持什么 lio 选项：

grep -R "DeclareLaunchArgument('lio" -n src/rm_nav_bringup/launch
grep -R "lio" -n src/rm_nav_bringup/launch/bringup_sim.launch.py

如果有 lio:=fake、lio:=none、lio:=fastlio 之类，可以先换轻量方案调 TEB。

  1. 如果必须用 Point-LIO，再去调 IMU 队列/频率

先找配置文件：

grep -R "max_imu_queue\|imu_queue\|imu_topic\|lid_topic\|publish_freq\|filter_size" -n \
  src/rm_nav_bringup/config \
  src/rm_localization \
  src

你现在这个警告不是 TEB 导致的，也不是 fake_vel_transform 导致的。它发生在 pointlio_mapping，优先从资源占用、IMU 频率、Point-LIO 配置处理。
