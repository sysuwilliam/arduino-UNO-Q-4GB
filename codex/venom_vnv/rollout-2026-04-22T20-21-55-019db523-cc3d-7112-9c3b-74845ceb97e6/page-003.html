就按这套做，但我先把每一步的含义讲清楚，这样你不会机械执行。

你现在这个 remote 已经是规范状态了，所以这组命令正好适用：

cd ~/venom_ws/src/venom_vnv
git fetch upstream
git checkout master
git merge --ff-only upstream/master
git push origin master
git submodule sync --recursive
git submodule update --init --recursive

含义分别是：

  1. git fetch upstream 从官方仓库抓最新提交，但不直接改你工作区。

  2. git checkout master 切回本地 master 分支。

  3. git merge --ff-only upstream/master 用“只允许快进”的方式，把你本地 master 更新到官方最新进度。 --ff-only 很重要，因为它不会随便产生一条 merge commit；如果你的本地 master 已经偏离，它会直接报错，提醒你先处理。

  4. git push origin master 把你本地更新后的 master 同步到你自己的 fork。

  5. git submodule sync --recursive 同步子模块 URL 配置，避免上游子模块地址调整后你这里还用旧地址。

  6. git submodule update --init --recursive 初始化并更新所有子模块到当前仓库记录的版本。

你实际使用时，建议这样理解：

  • 每次准备开始新任务前，先跑这一套
  • 然后再从最新 master 拉新分支

完整日常流程：

cd ~/venom_ws/src/venom_vnv
git fetch upstream
git checkout master
git merge --ff-only upstream/master
git push origin master
git submodule sync --recursive
git submodule update --init --recursive
git checkout -b feat/<topic>

有两个前提你要注意：

  1. git checkout master 前，当前工作区最好是干净的 用： bash git status 如果你还有未提交改动，先不要直接同步上游。

  2. git submodule update --init --recursive 可能会下载东西 如果网络慢或者子模块较多，会花一点时间，这是正常的。

你之前要求任何修改前都先说明。这里虽然不是改代码文件，但这组命令会更新本地仓库状态和子模块工作区，所以我先明确一下：

准备执行的操作： - 同步官方上游 master - 更新你自己 fork 的 master - 同步并更新子模块
