按你这个仓库当前状态，这个任务应该分成 4 段做，而不是直接上来改 YAML。

总流程

  1. 先确认 TEB 包本身是否可用
  2. 再在 nav2 配置里把 controller 从 DWB 切到 TEB
  3. 再补 launch / 依赖 / 参数
  4. 最后做联调和测试

第一步：确认接入前提

你先要确认两件事：

  1. 你的环境里有没有 teb_local_planner 对应 ROS 2 包
  2. 这个仓库到底是“只改主仓库配置就行”，还是要额外引入 TEB 源码/依赖

结合我刚才的检查，仓库里只有一份历史 TEB 参数文件： nav2_params_scoutmini.yaml

但当前默认使用的还是 DWB： nav2_params.yaml

所以你不能假设“项目已经完整支持 TEB”，要先确认运行环境里真有这个插件。

这一步建议检查：

ros2 pkg list | grep teb

以及后面启动时 controller_server 能不能识别： teb_local_planner::TebLocalPlannerROS

第二步：确定改动落点

如果只是把 Nav2 的局部规划器从 DWB 切换为 TEB，当前大概率只需要改主仓库内容，不是改子模块源码。

最可能的修改位置会在这些地方：

  • nav2_params.yaml
  • 可能还包括 scout_mini_mapping.launch.py
  • 如果你要给 sentry 也接，再看 nav2_params.yaml

具体要做的是：

  1. 把 controller_server.controller_plugins 保持为 ["FollowPath"]
  2. 把 FollowPath.plugin 从 dwb_core::DWBLocalPlanner 改成 teb_local_planner::TebLocalPlannerROS
  3. 把 DWB 参数块替换成 TEB 参数块
  4. 根据底盘类型重新调：
  5. max_vel_x
  6. max_vel_theta
  7. acc_lim_x
  8. acc_lim_theta
  9. min_turning_radius
  10. footprint_model
  11. 障碍物距离和优化权重

你仓库里那份历史 TEB 配置可以作为起点，但不能直接盲信，必须按你现在的机器人尺寸、速度、costmap 再调。

第三步：补齐依赖和运行条件

这一步常被忽略，但实际上决定你能不能跑起来。

你要确认：

  • TEB 插件库已经安装或纳入工作区
  • Nav2 启动时能加载这个插件
  • costmap、footprint、odom、TF 都和 TEB 假设一致

重点检查：

  1. package.xml / 依赖是否需要补充
    当前 venom_bringup 是 Python 包，本身不直接编译 controller，但如果项目文档或部署流程要完整，可能要把 TEB 依赖写清楚。

  2. 机器人模型是不是差速/阿克曼
    如果是差速车，min_turning_radius 通常可为 0.0；如果是阿克曼，参数要完全不同。

  3. 局部代价地图是否适合 TEB
    TEB 对 footprint、障碍物膨胀、局部地图更新频率比较敏感。

第四步：测试

测试不要一步到位上真机冲终点，建议分层测。

先做“能否启动”测试：

  1. colcon build
  2. source install/setup.bash
  3. 启动对应 bringup
  4. 看 controller_server 是否报插件加载错误

再做“基础跟随路径”测试：

  1. 给一个短距离目标点
  2. 看机器人是否能稳定起步、转向、停下
  3. 观察 /cmd_vel 是否连续平滑

再做“复杂场景”测试：

  1. 窄通道
  2. 急转弯
  3. 障碍绕行
  4. 低速贴边通过

你重点要看这些现象：

  • 是否频繁振荡
  • 是否原地左右摆
  • 是否路径跟随过度保守
  • 是否接近目标时抖动
  • 是否出现卡死或恢复行为频繁触发

建议你实际执行顺序

  1. 先确认环境里有没有 TEB 插件
  2. 先选一个平台，建议先只做 scout_mini
  3. 基于当前 DWB 配置复制一份新的 TEB 参数文件
  4. 让 launch 显式切到这份 TEB 参数
  5. 编译并做最小启动测试
  6. 再逐步调参
  7. 测通后再考虑是否覆盖默认配置

在这个项目里，你可以把 Nav2 简化成三层看。

1. bt_navigator：任务调度层

它负责接收“去哪里”的导航请求，比如：

  • NavigateToPose
  • NavigateThroughPoses
  • followWaypoints

然后按行为树流程去调下面的规划器、控制器、恢复行为。

你在 multi_waypoint_commander.py 里调用 BasicNavigator.followWaypoints()，最终就是在跟 bt_navigator 打交道。

2. planner_server：全局规划层

它负责从当前位置到目标位置生成一条全局路径。

你可以理解成： “从 A 点到 B 点，大致走哪条路。”

输出通常是一条 Path。

3. controller_server：局部控制层

它负责拿着全局路径、当前里程计、局部代价地图，算出机器人下一刻该怎么动，最后输出 /cmd_vel。

你可以理解成： “眼前这几米具体怎么走，怎么转，怎么避障。”

这里才是 DWB 或 TEB 所在的位置。

所以当前关系是：

  1. bt_navigator 收到导航目标
  2. planner_server 先算全局路径
  3. controller_server 再沿着全局路径做局部跟踪和避障
  4. 最后输出 /cmd_vel 给底盘
